# Group Chat Fixes + Identity Plan

## Summary
Fix duplicate group rows, group header duplication, description visibility, member search/1:1 navigation, sender identity in group messages, editable seed-based avatars, group membership locking/blocks, and avatar_seed exposure rules.

## Root causes
- Duplicate groups: `list_conversations()` joins `other_cm` for all conversations; groups multiply rows per member. Fix with direct-only lateral lookup.
- Header twice: ChatPage renders both `GroupHeader` and the normal `Avatar + h1` block. Render only one for groups.
- Description inactive: group description is loaded but not rendered in header/drawer. Render it under the group header and in the drawer.
- Search inactive: add-member search exists but needs to be the single group-list modal with clickable users.
- Avatars static: Identicon seed is hardcoded to user/conversation id. Add editable `avatar_seed` to profiles.
- Members table lacks enforcement: max 20 members, block behaviour, unique member key, block-respecting RPCs not yet defined.

## Changes
1. Backend migration:
   - `DROP FUNCTION list_conversations()` old signature; recreate with `search_path = public, private, pg_temp`; same-migration REVOKE/GRANT; catalog test (anon cannot execute; exactly one overload exists).
   - Groups return one row in `list_conversations()`; direct chats use lateral other-member lookup.
   - Add `profiles.avatar_seed text`; `update_avatar_seed(p_seed text)` RPC; expose `avatar_seed` in `getCurrentUser`/`listGroupMembers`/conversation mapping.
   - Verify `UNIQUE(conversation_id, user_id)` on members; if duplicates exist, show cleanup query before adding constraint. No `ON CONFLICT DO NOTHING` to hide errors.
   - Add-member RPC enforces max 20 members under a lock.
   - Generic `OPERATION_FAILED` errors for blocked add-member / blocked send / member-to-DM attempts; never reveal a block.
   - RPCs for remove, rename, edit description, delete, leave — each with `auth.uid()` checks and rate limits. Creator leaving behavior; group deletion behavior (reports keep message snapshots).
   - `update_avatar_seed`: allow only `^[A-Za-z0-9_-]{1,32}$`, rate-limited, `auth.uid()` required. Decide seed-only vs seed+palette; store accordingly. `avatar_seed` visible only to users who share a conversation; never to signed-out visitors.
2. ChatPage:
   - For groups render only `GroupHeader` (avatar + title + member count + description snippet); remove duplicate h1/avatar.
   - `loadMessages` returns sender display name + username per message (former members stay resolvable) so messages from people who left still show a name.
3. GroupSettingsDrawer:
   - Single modal with member list + search; creator sees Add; everyone sees members.
   - Description shown for all; creator can edit.
4. Settings:
   - Add avatar seed/palette picker; save via `updateAvatarSeed`. Decide seed-only vs seed+palette; store accordingly.
   - Use `avatar_seed` everywhere Identicon is rendered so changes propagate to groups/friends.
5. Member modal:
   - Filtering existing members is client-side; adding uses exact-username lookup. No browse or prefix search.
   - Member tap calls `getOrCreateDirectConversation(member.userId)` respecting blocks and rate limits; recommend whether an "allow messages from group members" setting is needed.
6. Cleanup:
   - Ensure one group row per conversation; add integration assertion.

## Implementation order
1. Migration: list_conversations drop/recreate with search_path + REVOKE/GRANT; avatar_seed; update_avatar_seed; UNIQUE(conversation_id, user_id) with cleanup query if duplicates; max-20 under lock; block-aware RPCs (add/remove/rename/edit-description/delete/leave); rate limits.
2. Types/database/api mapping; api.ts updated with api.mock.ts + parity test in the same step; PR labelled `contract`.
3. SQL tests as authenticated users: non-member cannot read members/messages; non-creator cannot add/remove/rename; 21st member refused; blocked add fails generically; invalid seed rejected; concurrent-add race test.
4. ChatPage header/description/sender identity/member navigation (loadMessages sender name + username).
5. Drawer search/member click (client-side filtering; exact-username add).
6. Settings avatar picker.
7. Member tap 1:1 navigation (block + rate limit respected; setting recommendation).
8. Tests + manual validation; usage estimate for Realtime messages in 20-member groups at 1,000 and 10,000 users vs free 2M/month.

## Decisions
- Avatar editing: seed/palette only, no upload — decide seed-only vs seed+palette and store accordingly.
- Sender UI: avatar + display name + @username above each group bubble; former members resolvable.
- Group header: single trigger opening member modal.
- Member click: start/open 1:1 without leaving group; blocks + rate limits respected; "allow messages from group members" setting recommendation pending.
- Creator-only add/remove/rename/delete; members leave; creator leaves behavior defined; group deletion keeps report message snapshots.
- Max 20 members enforced under lock in add RPC.
- Block behaviour: all failures generic (`OPERATION_FAILED`), never revealing a block, for add-member, send, and member-to-DM.
- Member modal: client-side filtering of existing members; exact-username lookup for adding; no browse or prefix search.
- `avatar_seed` visible only to conversation-sharers; never to signed-out visitors.
- `api.ts`/`api.mock.ts`/parity test updated together; PR labelled `contract`.
